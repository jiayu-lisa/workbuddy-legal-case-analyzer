# 模块 C：争议焦点分层拆解

## 一、适用时机与输入

- **触发**：用户要求"拆解争议焦点""本案有哪些争议焦点""帮我梳理争点"等。
- **输入**：本案案情 + 已识别出的法律问题清单。若对话中尚无，先复用模块 A 的案情梳理成果；法律问题清单缺失时，先基于案情补足再拆解，或一次性追问，不挤牙膏。

## 二、方法论：三层拆解 + 焦点细化 + 焦点关系

### （一）三层拆解

把争议焦点按性质分为三层，**严格区分事实问题与法律问题**：

1. **事实层面的争议**：双方对哪些事实的认定可能有分歧。如"回购条件是否已成就""股权转让是否已实际履行并变更登记""某笔款项的性质是出资还是借款"。
2. **法律适用层面的争议**：对同一事实，应适用哪条法律、如何解释。如"回购义务的性质是股东身份义务还是合同义务""该条款是否属于无效的保底条款"。
3. **程序层面的争议**：管辖、当事人主体资格、诉讼时效、举证责任分配、案由、是否重复起诉等。

**提示**：事实层面争议往往依赖模块 B 的事实缺口核实结果；程序层面争议常具有"一票否决"效力，应优先排查。

### （二）焦点细化（仅针对法律适用层面）

对每一个**法律适用层面**的争议焦点，进一步拆解为**可独立检索的子问题**。子问题要具体到能单独作为一次检索的主题。

示例——"股权转让是否影响回购义务"可拆解为：
- 回购义务的性质是基于股东身份还是基于合同约定？
- 合同义务是否因义务人丧失股东身份而消灭或转移？
- 股权受让人是否当然承继原股东的回购义务？

细化标准：每个子问题应能独立用法条或类案回答；若一个子问题仍包含两个以上可分开检索的点，继续下拆。

### （三）焦点关系图（逻辑链条）

说明各争议焦点之间的逻辑关系：

- **前提与结果**：哪些焦点是前提，哪些焦点的讨论以其为前提。如"只有先认定回购义务成立（焦点1），才有讨论其是否因股权转让而消灭（焦点2）的必要"。
- **决定走向**：哪个焦点的认定结果会直接决定案件走向（通常是核心法律适用焦点或程序性焦点）。
- 默认用**一段文字**描述逻辑链条即可；用户要求图形化时再配图（见 SKILL.md 可视化约定）。

## 三、输出模板

严格用**三级编号结构（一、1、（1））**，最后用一段文字描述焦点之间的逻辑链条：

```
一、分层拆解
1. 事实层面的争议
   （1）……
   （2）……
2. 法律适用层面的争议
   （1）……
   （2）……
3. 程序层面的争议
   （1）……（管辖/主体资格/诉讼时效/举证责任分配等）

二、焦点细化（针对法律适用层面）
1. 关于焦点【法律适用焦点（1）的表述】，可拆解为以下可独立检索的子问题：
   （1）……
   （2）……
   （3）……
2. 关于焦点【法律适用焦点（2）】：
   （1）……

三、焦点关系图
（一段文字描述逻辑链条：哪些是前提、哪些是结果、哪个焦点的认定结果直接决定案件走向）
```

## 四、质量自检

- [ ] 三层是否严格区分，事实问题与法律问题未混杂？
- [ ] 程序层面是否单独排查（管辖、主体资格、时效、举证责任）？
- [ ] 每个法律适用焦点是否都细化成了可独立检索的子问题？
- [ ] 是否用一段文字说清了焦点间的前提/结果/决定走向关系？
- [ ] 涉及法条、案例处是否遵守引用规范（名称+条号+现行有效+生效日期；案号+法院+裁判日期）？不确定处是否标注"需核实/待核实/我不确定"？
